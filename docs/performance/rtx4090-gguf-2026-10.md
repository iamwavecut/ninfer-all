# RTX 4090 GGUF vector experiment, October 2026

This experiment targets the existing IQ3_S vector product in the public Engine.
The candidate is opt-in, not an adopted speedup. No new CUDA path is enabled by
default. The BF16x8 SiLU experiment from PR #2 remains disabled in both arms.

## Target and dispatch

The only changed kernel is `vec::kernel<GGML_TYPE_IQ3_S,6,false,5120>`.
`NINFER_ADA_GGUF_IQ3S_T6_LOOP=ON` leaves its five K iterations rolled rather
than fully unrolling them. It retains two rows per warp, four warps per block,
the shared IQ3_S codebook, activation quantization, integer DP4A products,
accumulation order, output conversion and occupancy-based launch sizing.
The define applies only to `ggml_vec_iq3_s.cu`; CMake rejects the option unless
the build contains only architecture 89. Other types, K values, T values,
fused products and architectures keep their existing routes.

`gguf_linear.cpp::gguf_project` uses planar q8_1 activations for vector-width
products and reuses them for compatible input gathers. The bridge dispatches
the stored GGUF type, then column count, fusion and static K. Wider products
retain their existing MMQ/dequantize-and-GEMM routes. DFlash2 with five draft
tokens exercises T=6 verification; ordinary single-request decode exercises
T=1 and is a negative control for this candidate. No model schedule, artifact,
runtime allocation or Engine interface changes are involved.

```powershell
.\scripts\build-rtx4090.ps1
.\scripts\build-rtx4090.ps1 -ExperimentalGgufIq3sT6Loop
```

The second command defaults to a distinct `build-rtx4090-iq3s-t6-loop` directory.
Keep SFU and vector SiLU options off for comparisons.

## Existing Nsight evidence

The retained Systems node profiles use the same artifact, rk4v4, CUDA Graphs,
128 generated tokens, one measured repetition after one warmup, and a 4096-token
capacity. DFlash2 uses five draft tokens. Cumulative kernel times include all
calls in those captures; they are not unprofiled Engine throughput.
Aggregating the vector products across K and fusion gives IQ3_S
635.130 ms/30.53% (plain) and 354.881 ms/26.85% (DFlash2), followed by
IQ4_XS 23.43%/18.45%, IQ3_XXS 17.27%/14.41% and Q4_K 12.37%/11.14%.

output [N,T]; a fused gate/up parent has [2N,K]. The artifact's K=5120

projection parent. A capped grid alone would not reveal N. Numerical
qualification includes both [6144,5120] and this [10240,5120] shape.

T=6 is register-limited but the six-register reduction does not cross an
occupancy boundary. Both profiles report zero local/shared spilling requests.
SM clocks were 2.48/2.49 GHz and memory clocks 10.48/10.47 GHz; the runs were
not clock-identical. Compute utilization is 35.79%/36.96% (baseline/rolled),
below memory utilization; the baseline profile identifies long-scoreboard
stalls and only 0.48 eligible warps per scheduler per cycle. This supports a
memory delivery/latency bottleneck, not an established DP4A throughput limit.
The SASS counters report 2,457,600 executed warp DP4A instructions in both
T=6 variants (78,643,200 active thread instructions). Dividing by the captured
durations gives 2.60/2.68 trillion thread DP4A instructions/s. Static DP4A sites
fall from 480 to 96, but total executed warp instructions rise from 11,065,344
to 12,724,224. The rolled loop trades code size for loop/control instructions;
it does not reduce mathematical work. Single replay profiles do not establish
a stable latency or Engine improvement.

Higher occupancy alone was insufficient. The earlier six-pair one-row
Engine campaign included plain-decode changes from -10.70% to +7.29% and
DFlash2 changes from -8.93% to -0.65%; a repeat still included a -5.08%
long-context DFlash2 result. That implementation was rejected. An earlier
all-static-K rolled candidate had mixed results (plain -4.23% to +8.80%;
the two completed DFlash2 pairs -5.05% to +4.96%). Its campaign was incomplete.
The selected implementation was restricted to the profiled K=5120 before
starting the new campaign, avoiding an unsupported schedule change at K=17408.

## Numerical contract and measurement method

The GPU linear test independently decodes IQ3_S bytes on the host using the
published codebook, stored half scale, sub-block scales, signs and indices.
It first requires exact agreement from the GPU dequantizer, then uses the host
weights and represented BF16 inputs in a naive FP64 matrix product. The public
GGUF product's q8_1 activation quantization and final BF16 conversion are included
in its existing error budget: error L2/reference L2 <2% and max absolute
error/max absolute reference <8%; fused SwiGLU has twice that budget.
This tests represented-input error, not bitwise FP64
equivalence. Tests cover plain, gathered, residual-add, fused and paired SwiGLU,
and exact BF16 embedding, including N=6144/K=5120/T=1,6 and
N=257/K=5120/T=5,6,7, plus the profiled N=10240/K=5120/T=6.
The 257-row case checks row tails and neighboring routes.

Both benchmark arms use native sm_89, CUDA 13.4, MSVC 19.44, driver 617.42,
the built-in 4090 device profile and a 450 W limit. Clocks are not locked.
The artifact is opened read-only at
`C:\ninfer-all\models\Huihui-Swift15-Abliterated-IQ3S-DFlash2.ninfer`
(15,017,456,896 bytes), without copying or converting it.

The CPU-only runner starts a fresh public `ninfer_bench` process per arm,
alternates AB/BA across six pairs, and reverses the starting order for DFlash2.
Every process measures pp512, pp2048, tg128 and pp512/2048/8192+tg128,
with two repetitions, one warmup, rk4v4, graphs, prefill chunk 1024 and
max context 16384. The input is `bench/fixtures/bench_corpus.ids`.
Both arms are built with SFU and BF16x8 SiLU OFF. Baseline has the IQ3_S option
OFF; candidate has it ON. Sampled telemetry includes process loading and idle
periods as well as measured work, so its medians are not kernel-only values.

For separate build directories, first stage each executable beside the baseline
DLL closure under distinct names; do not replace either arm during a campaign.
The main series used `ninfer_bench_iq3s_ttft_base.exe` and `ninfer_bench.exe`.
After restoration, reproduce with the archived candidate and ordinary baseline:

```powershell
py -3.11 tools/bench/compare_gguf_iq3s_4090.py `
  --base C:\coding\ninfer-all\build-rtx4090\bench\ninfer_bench.exe `
  --candidate C:\coding\ninfer-all\build-rtx4090\bench\ninfer_bench_iq3s_k5120_candidate.exe `
  --weights C:\ninfer-all\models\Huihui-Swift15-Abliterated-IQ3S-DFlash2.ninfer `
  --out C:\coding\ninfer-all\profiles\bench\iq3s-k5120-reproduction-01 --pairs 6
```

Benchmark JSON schema 19 now exports the existing Engine `first_token_seconds`.
This is TTFT including preparation, not a sum of phase timers. The initial new
run was stopped after discovering that the previous controller's TTFT was only
a prepare+vision+prefill proxy; those legacy timing values are not used as TTFT.
The matrix, tuner and speed-of-light readers/tests move together to schema 19.
One test build attempt omitted `-Test` and had no `ninfer_tests` target;
the corrected build enabled testing and passed the affected tests.
During restoration, the third successive wrapper invocation in one PowerShell
process failed to import the Visual Studio PATH. CLI and benchmark restoration
had already succeeded. A fresh-shell test build was used instead; this does not
change the completed benchmark measurements. Repeated same-shell wrapper
initialization remains a local tooling limitation.
The initial token controller also inherited Windows CP1252 output decoding,
which corrupted UTF-8 German text in its logs. Completed token-ID comparisons
were equal, but the incomplete text-log campaign was stopped. The controller
now decodes strict UTF-8 and the complete token matrix was restarted in
`profiles/bench/iq3s-k5120-4090-quality-utf8-20261022`. Benchmark numerical JSON
was already read explicitly as UTF-8 and its metrics were not affected.

Telemetry samples approximately every 250 ms plus collection overhead. Graphics
clock, temperature, board power and total device VRAM come from nvidia-smi.
Process dedicated VRAM comes from the Windows PDH `GPU Process Memory` counter
for the launched PID, since NVML reports N/A under WDDM. These are sampled peaks,
not guaranteed instantaneous allocator maxima. Total device VRAM also includes
the desktop and other applications. Raw process reports, stderr/stdout and
telemetry stay under `profiles/bench/iq3s-k5120-4090-ab-20261022`.

The six-pair main series does not establish a stable Engine speedup. Plain
decode case medians range from -0.30% to +0.63%, with individual paired changes
from -9.20% to +8.16%. DFlash2 case medians range from -1.63% to +2.35%, with
individual changes from -9.01% to +7.11%. These adverse results are not discarded
as noise. Two additional complete alternating pairs per mode repeat the same
matrix after the main series, without changing acceptance criteria. This is an
experimental schedule candidate, not an improvement to recommend enabling.

The repeats retain significant regressions: plain 8192-token decode is -8.17%
and -7.05% in the two pairs; DFlash2 includes -4.84% at 8192 in one pair and
-7.18%/-8.02% at 512/2048 in the other. They are not reclassified as noise.
To check the negative control, `cuobjdump --dump-sass --function` compared
`vec::kernel<IQ3_S,1,false,5120>` in the restored baseline and archived candidate.
Its complete SASS dumps match exactly (one function, 1840 instruction lines).
This establishes that this T=1 kernel's machine code is unchanged; it does not
explain or invalidate the whole-Engine regressions. Their cause remains
unresolved, and no performance adoption is justified.

The candidate binaries were archived beside the same DLL closure as
`bench/ninfer_bench_iq3s_k5120_candidate.exe` and
`apps/ninfer_iq3s_k5120_candidate.exe` after the main series. The ordinary
`ninfer_bench.exe`, `ninfer.exe` and test bundle were rebuilt with all experimental
options OFF. The repeat series and token checks use these distinct names.
Other architectures were not executed or performance-qualified. No end-to-end
speed claim is made from the Compute single-kernel measurements.

### Token identity

All baseline/candidate comparisons below agree on prompt length, all 64
generated IDs and the complete UTF-8 text. Plain decode and DFlash2 are **not**
token-identical to each other: the first differing token is 34 for `cuda`,
35 for `german` and 8 for `long` (one-based), identically in baseline and
candidate. This existing backend difference is not attributed to the loop
candidate, and its cause was not diagnosed here. These checks establish A/B
identity within each mode, not cross-backend identity, language quality,
retrieval accuracy or perplexity.

Per-process rates, TTFT, clock/temperature ranges, power and sampled VRAM peaks are in
[the complete CSV](rtx4090-gguf-2026-10-processes.csv). Each process appears once per case;
telemetry fields repeat across its six cases. Throughput changes above are candidate/base;
positive TTFT changes mean slower first-token delivery. Tables retain all pairs and exceptions.

Across the main and repeat series, process-median graphics clocks span
2460–2565 MHz, process peak temperatures 65–76 C and sampled peak board power
449.89–463.73 W. Sampled PID-dedicated peaks are 12,306.24 MiB for every plain
process and 14,940.26 MiB for every DFlash2 process, for both arms. Engine
weight allocations are 11,755,300,864 / 14,360,105,472 bytes and runtime
reservations 777,395,456 / 1,288,603,904 bytes (plain / DFlash2), equal between
arms. Device-wide VRAM varies with the desktop; use the PID column for the
per-process comparison. No memory-saving claim is made.

Both restored baseline and archived candidate passed the complete affected
GGUF numerical suite; the benchmark report contract passed, as did all 21
affected Python tests and Python 3.11 compilation checks. Documentation links
and `git diff --check` were checked. No other GPU architecture, larger than
8192-token performance workload, or model artifact was qualified.
