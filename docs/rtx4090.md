# RTX 4090 (Ada, sm_89) development workflow

This is an opt-in workflow for a 24 GB GeForce RTX 4090 on native Windows. It builds a
single `sm_89` CUDA image rather than relying on `sm_86` forward compatibility.
**An `sm_89` build is not by itself a performance improvement**: verify a change against
the same weights, request fixture, driver and clocks before claiming a gain.

## Build

Requirements: VS 2022 Build Tools with the C++ workload, Ninja, CMake, the project
dependencies, a recent NVIDIA driver and an installed CUDA toolkit. The default
4090 wrapper selects CUDA 13.4; pass `-CudaVersion 12.8` or another supported
installed version to select a different one. The generic `build.ps1` retains its
earlier CUDA 12.8/12.9 preference when no version is selected.

```powershell
.\scripts\build-rtx4090.ps1
.\scripts\build-rtx4090.ps1 -Clean -Test
```

The product binaries and the `ninfer_bench.exe` public-Engine benchmark are built
into `build-rtx4090`. Existing `build-ninja` binaries are left untouched.

## Calibrate and benchmark

Close games, other inference servers and GPU workloads. For a newly built binary,
calibrate its measured kernel route candidates on the actual board before
comparing workloads; calibration results are stored by the engine and override
only the measured route keys. Keep a copy of the device profile and its build
provenance when reproducing results.

```powershell
.\build-rtx4090\apps\ninfer-calibrate.exe --device 0 --detail
.\scripts\benchmark-rtx4090.ps1 -Model 'C:\models\qwen3_8_27b.ninfer' -Preset smoke
.\scripts\benchmark-rtx4090.ps1 -Model 'C:\models\qwen3_8_27b.ninfer' -Preset core
```

Use `-Preset full` for additional longer-context cases. The matrix writes
`summary.csv`, `summary.json`, per-case JSON and logs, plus `rtx4090-host.json`
with driver/power settings and model metadata under `profiles/bench/rtx4090-*`.
The existing matrix primarily tests MTP; compare DFlash2 independently using
`ninfer_bench` or the server's reference benchmark. The smoke/core/full test
cases are defined in `tools/bench/run_ninfer_bench_matrix.py`.

On multi-GPU Windows machines, run `build-rtx4090\tools\ninfer-multi-gpu-probe.exe`
to check CUDA indices; `nvidia-smi` GPU indices may differ. `-Device` sets the
benchmark CUDA device index, not the `nvidia-smi` index.


## Experimental Ada SFU kernel path

The project's CUDA kernels already have optional SFU approximations for sigmoid/SiLU
and the GDN softplus gate. They may reduce instruction cost but can alter rounding,
so the RTX 4090 build keeps the original path unless explicitly requested:

```powershell
.\scripts\build-rtx4090.ps1 -Test
.\scripts\build-rtx4090.ps1 -ExperimentalFastSfu -Test
```

The opt-in candidate builds to `build-rtx4090-sfu`, distinct from
`build-rtx4090`.

For a paired A/B speed comparison, build both configurations, then run:

```powershell
.\scripts\compare-rtx4090-sfu.ps1 -Model "C:\models\qwen3_8_27b.ninfer" -Repetitions 6
.\scripts\compare-rtx4090-sfu.ps1 -Model "C:\models\qwen3_8_27b.ninfer" -Spec dflash2 -DraftTokens 5
```

This uses the existing interleaved A/B runner with alternating baseline/SFU
process order. It stages the SFU executable beside the baseline executable
for correct Windows DLL lookup and deletes that temporary copy afterwards.
It does not qualify the alternate arithmetic for numerical accuracy. The switches map to `NINFER_SFU_SIGMOID_SILU` and
`NINFER_SFU_SOFTPLUS`. Keep SFU off in the production build unless
the candidate passes GPU numerical regression tests and an interleaved A/B
comparison shows a reproducible gain for the actual artifact and workload.

## Experimental aligned SiLU kernel

`-ExperimentalVectorSilu` builds an opt-in sm_89 variant in
`build-rtx4090-vector`. Aligned contiguous BF16 arrays divisible by eight and
at least 262,144 elements use
16-byte loads and stores per lane, with the existing FP32 SiLU and BF16 rounding.
Other layouts and tails retain the old route. Compare
`ninfer_silu_mul_bench` from both builds in alternating order, then whole
requests with identical artifact, tokens, graph setting and KV format.
Record driver, build hash, temperature, power and peak VRAM. The direct kernel
probe is `tools/bench/silu_ada_probe.cu`; from an x64 VS 2022 developer shell,
compile it with:

```powershell
nvcc -std=c++17 -arch=sm_89 -O3 -I. -Isrc `
  -o build-rtx4090-vector/silu_ada_probe.exe tools/bench/silu_ada_probe.cu
.\build-rtx4090-vector\silu_ada_probe.exe
```

On one RTX 4090 (driver 617.42, CUDA 13.4, 37 C and 52.93 W before the
run), the direct probe compared six alternating pairs of 2,000 launches in
the same executable, twice. Ranges of the two median baseline/candidate
kernel times, in microseconds:

| Elements | Baseline | BF16x8 | Median ratio | Worst paired ratio |
|---:|---:|---:|---:|---:|
| 17,408 | 4.44-5.12 | 4.37-5.45 | 0.94-1.02 | 0.86 |
| 278,528 | 4.79-5.03 | 4.42-4.53 | 1.08-1.11 | 1.06 |
| 557,056 | 5.56-5.76 | 4.81-5.08 | 1.13-1.16 | 0.87 |
| 835,584 | 7.08-7.62 | 5.12-5.38 | 1.38-1.42 | 1.03 |

At every measured size the candidate agreed bit for bit with the baseline;
the independent FP64 SiLU oracle had zero failures under the probe's BF16
criterion, including odd tails on the fallback. These are direct kernel
measurements, not end-to-end inference gains. The 17,408-element decode
shape was inconsistent and the new dispatch excludes it. The 557,056-element
case includes a slow paired sample despite faster medians; repeat measurements with stable clocks
before adopting the route by default. Peak VRAM and per-run power were not
captured.

## Measured inference configuration tuning

The CPU-only Python controller repeatedly starts the public Engine benchmark,
rotates candidate order across rounds, and measures plain decode by default.
Use `--backends mtp dflash2` only when the artifact contains those components;
this adds MTP3/5 and DFlash2-3/5/7 with `rk4v4`. The full matrix also compares
`rk8v4` and a 32,768-token prompt.

```powershell
python tools/bench/tune_rtx4090.py --weights "C:\models\qwen3_8_27b.ninfer" `
  --bench "build-rtx4090\bench\ninfer_bench.exe" `
  --out "profiles\bench\4090-auto-01" --preset quick --rounds 3 --backends mtp dflash2

python tools/bench/tune_rtx4090.py --weights "C:\models\qwen3_8_27b.ninfer" `
  --bench "build-rtx4090\bench\ninfer_bench.exe" `
  --out "profiles\bench\4090-auto-full-01" --preset full --rounds 3 --backends mtp dflash2
```

Use a new `--out` directory on every run. The tuner saves every benchmark's
raw JSON, stderr/stdout, `samples.json`, and `recommendations.json`. It checks
that the Engine report names an RTX 4090, that each run measures the requested
length, and requires every repetition to succeed. Under 3% improvement it
retains the non-speculative `rk4v4` baseline. Only declare backends contained
in the artifact; a declared but unsupported backend remains visible as failed.

**Limitations:** the tuner compares output *speed*, not linguistic quality or
retrieval correctness. Different KV storage types and approximated CUDA
arithmetic require separate long-context recall/perplexity checks before
production selection. The controller is not an online token-by-token
adaptive decoder; it produces suggested launch flags based on one fixed corpus.

## Optimization campaign

1. Establish `sm_86` versus `sm_89` paired baselines on the same RTX 4090,
   controlling GPU temperature and clocks.
2. Measure prefill chunk size, CUDA Graph versus eager decode, KV formats
   (`rk4v4`, `rk8v4`) and context lengths without changing weight artifacts.
3. Sweep MTP/DFlash2 draft counts and measure verified output tokens/sec,
   acceptance, latency, memory and long-context retrieval correctness.
4. Profile the hottest GPU kernels (Nsight Systems/Compute), change **one**
   bottleneck per branch, and validate with the interleaved A/B runner.

Existing reference performance for this board is documented in
[performance](performance.md) and [device profiles](device-profiles.md);
comparisons across different hosts or models are not apples-to-apples.
